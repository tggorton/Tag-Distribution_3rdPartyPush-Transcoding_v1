Read this first

A behavior prototype, not a partial build

There's no backend — the transcode itself is simulated (a timer), and all state lives in the browser (localStorage). The job is to pin down the intended behavior and screens so the team can scope and build the real pipeline. Most importantly: the backend owns the transcode lifecycle; the UI only reflects it and offers a restart.

Foundations (shared with 3rd-Party Push)

Two status lifecycles. Every distribution tag carries two independent statuses, one column each: Transcode Status (this doc) and Platform Status (the Push doc). A tag can be transcoded and live yet never pushed. Roles: a user/admin toggle gates admin tools, which appear as an edit pencil next to a dropdown inside a modal. Readability: each status is a colored dot and a label; same-hue states are told apart by a ring-vs-solid dot.

Everything it entails

Feature inventory

Every unique behavior the Transcoding track adds, at a glance. Each is detailed in the sections that follow.

Applying presets

  • Transcoding Settings modal — applies one or more presets; every distro is transcoded once per preset.
  • ~15 fields grouped Video / Audio, shared by every preset — presets differ only in values.
  • Standards-backed inputs — Duration is a dropdown of spec durations; Video Bitrate is a multi-select of single rates (no ranges).
  • Read-only for users — regular users pick presets only; the field sheet can't be overridden.
  • Collapsible rows + + Add Preset (inserts at top, scrolls to it).
  • No duplicate presets — an applied preset is greyed out in other rows; + Add Preset disables once all are used.
  • Incremental apply — only new/changed presets reprocess.

Presets & admin catalog

  • Presets are publisher specs (Hulu, Disney+, Netflix, …). DSPs are push targets, not presets.
  • Mutable admin catalog — a pencil opens Save New / Update / Delete. The Default baseline is protected. Custom values & field edits are admin-only, made here.
  • Updating a preset re-transcodes every distribution using it, across the line item.
  • Bitrates trace to published specs where available (Disney+/Hulu, Prime, Peacock, Roku, …).

Transcode Status (per distro)

  • A dedicated Transcode Status column, independent of Platform Status.
  • Five states — Default / Live / Processing / Error / Inactive. (No "Out of Spec" — presets can't be overridden.)
  • One chip per applied preset, stacked, each naming its publisher.
  • Restart row icon — enabled only when Inactive or Error; confirms first.

Prototype-only (gone in production)

  • ⋯ menu "Set transcode status" to force any state.
  • Processing → landing is a fixed timer, standing in for the pipeline.
The settings

What it does

Transcoding Settings (a button in the Distributions section, available to all users) opens a per-line-item panel that applies one or more presets. Every distribution tag is transcoded once per preset, and each tag's applied presets show as a stack of chips in its Transcode Status column.

  • The panel is a list of preset rows, each a preset picker over the shared field sheet. Rows are collapsed by default; expand (chevron) to view the fields. For regular users the sheet is read-only — you select a preset, you don't edit its fields.
  • Picking a preset fills that row's sheet. The only way to change a preset's values is for an admin to edit the preset itself (pencil → catalog manager); that change then propagates to every line item using it.
  • + Add Preset inserts a new row at the top and scrolls to it. Delete drops a row; deleting the last one confirms and resets to the Default baseline.
  • Incremental apply — applying only reprocesses new or changed presets; unchanged presets keep each distro's current status.
New — standards-backed inputs

Duration & Video Bitrate

Two fields that used to be free text are now spec-backed selectors. Video Bitrate is a multi-select of single, fixed rates — no ranges, no averaged bands, so a preset can carry several rates at once. The ladder (1–50 Mbps) is grounded in public specs (IAB 2026, The Trade Desk, Amazon, Disney/Hulu, Prime, FreeWheel, DV360 — checked 2026-10-14), chosen so at least one rate falls inside every known publisher range. Custom rates are admin-only: in the preset catalog manager, typing a valid single number surfaces an explicit “Add custom rate…” entry (a range is rejected). Regular users pick from the ladder.

Duration

  • 15s · 30s · 45s · 60s · Original, plus Custom.
  • Original keeps the source runtime intact — a 30.89s clip stays 30.89s. Choosing it shows an amber caution: a non-standard length may be flagged in publisher testing.
  • A fixed value (e.g. 30s) trims to exactly that length.

How Custom works (admin)

  • Only an admin editing a preset can type a custom rate — users pick from the ladder.
  • A typed rate is kept as a chip with a "Custom" badge and joins the preset's renditions.
  • Non-rate input is ignored; the ladder only accepts single fixed rates (e.g. 18 Mbps), never ranges.
Bitrate — grounded in specs

Why a ladder of single rates

The platform needs fixed rates, not ranges. So instead of range options, the field offers a ladder of single rates picked so at least one lands inside every published spec band. A preset can select several at once. Full provenance lives in-repo at docs/reference/video-encoding-bitrate-reference.md.

The ladder: 1 · 2 · 3 · 4 · 5 · 6 · 8 · 10 · 12 · 15 · 20 · 25 · 30 · 40 · 50 Mbps. A few landmark rates and the specs they satisfy:

Caveat

The IAB 2026 figures are from a public-comment draft, and the single rate chosen for each publisher is a representative value inside its published band, not a publisher-mandated number. Confirm against each target publisher's current spec before production.

No "Out of Spec" state — presets can't be overridden, so nothing can diverge from a publisher spec. One chip per applied preset. Each tag shows a stack — e.g. Live: Hulu (Disney) above Live: Netflix. Scoping the real build

Prototype vs. production

In the prototype

  • Preset bitrates trace to specs where published; other field values are illustrative.
  • Processing → landing is a fixed timer, not a real transcode.
  • Option lists are a flat superset (any rate on any preset).
  • Updating a preset re-transcodes its distros across this line item (scope TBD for prod).
  • Catalog edits persist to localStorage.

For production

  • Load real publisher specs; likely constrain valid rates per publisher in the admin editor.
  • Apply (and an admin preset update) kicks a real re-transcode; status arrives from the pipeline (webhook / poll).
  • Confirm the real propagation scope of a preset update (whole account? this line item? immediate vs. queued).
  • Persist the admin preset catalog server-side with real auth.

Try it

Walkthrough

Add a distribution tag

Distributions → + Add Distribution Tag. It appears with one Transcode Status chip per applied preset.

Apply multiple presets

Transcoding Settings → change the first row to Hulu → + Add Preset → set it to Netflix → Apply. Every tag now shows two chips.

See the read-only sheet

Expand a preset row. As a regular user the fields are read-only — Video Bitrate shows the preset's selected single rates as chips; you select presets, not field values.

Edit a preset as admin

Flip the top-bar toggle to Admin, open the pencil beside the preset picker, and edit a preset. In Video Bitrate pick several single rates (each a rendition) or type a custom rate; Update re-transcodes every distro using that preset.

Watch the re-transcode land

After Apply or an admin Update, affected tags go Processing → then Live (or Default on the untouched baseline). A failed run shows Error, where the row's restart re-runs it.
