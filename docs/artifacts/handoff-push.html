3rd-Party Push

Read this first

A behavior prototype, not a partial build

There's no backend and no real auth — all state lives in the browser (localStorage), and every external call (advertiser lookup, push) is simulated. Its job is to pin down the intended behavior and screens so the team can scope and build the real thing. Throughout, each feature is split into what the prototype does vs. what production must own.

Foundations (shared with Transcoding)

Two status lifecycles. Every distribution tag carries two independent statuses, one column each: Platform Status (this doc) and Transcode Status (the Transcoding doc). A tag can be transcoded and live yet never pushed — or pushed and rejected. Platform, not DSP: today a platform is a DSP (Nexxen, The Trade Desk); the naming deliberately spans DSP and SSP so supply-side targets fit later. Readability: each status is a colored dot and a label; same-hue states are told apart by a ring-vs-solid dot.

Everything it entails

Feature inventory

Every unique behavior the 3rd-Party Push track adds, at a glance. Each is detailed in the sections that follow.

Pushing tags

  • Push Tags to Platform dialog — pick a platform + advertiser, choose which tags, push.
  • Platform-drives-selection — choosing a platform auto-selects its tags and disables the rest.
  • family→platform lock — a tag can only be pushed to the platform it was built for.
  • Partial push — uncheck any tags; live "N of M selected" count + count-aware button.
  • Add + Push / Save + Push — push straight from the tag editor, pre-scoped.

Advertiser model

  • Platform-scoped advertisers — each platform returns its own set (dependent dropdown).
  • Name + ID display — Advertiser 1 · 012345.
  • One advertiser per platform, locked — first push sets it; then disabled with a lock icon + "contact support" tooltip.
  • Async load with a stale-response guard.

Platform Status (per distro)

  • A dedicated Platform Status column, independent of Transcode Status.
  • Five states — Not pushed / Pushing / Success / Error / Inactive — the chip names the destination.
  • Link / Unlink row icon — unlink Success → Inactive; relink Inactive/Error → Success. Both confirm first.

Prototype-only (gone in production)

  • ⋯ menu "Set platform status" to force any state during a walkthrough.
  • Optimistic push (always lands Success).
  • Mocked advertiser lists with simulated latency.
The push flow

What it does

Push Tags to Platform (a button in the Distributions section, disabled until at least one tag exists) opens a dialog to choose a destination and exactly which tags to send.

  • Advertisers are scoped to the platform — each platform returns its own set — so the platform must be chosen before the advertiser field enables.
  • Each advertiser shows as name + advertiser ID (Advertiser 1 · 012345; the ID format is a placeholder).
  • One advertiser per platform, locked. The first push to a platform sets its advertiser; every push after that reuses it and the field is disabled — greyed, with a lock icon and a "contact support to change the advertiser for this platform" tooltip. Changing it is deliberately a support operation, not a self-serve control, because linking a platform + advertiser is non-trivial on the backend.
  • The advertiser list loads asynchronously with a spinner, and a stale-response guard keeps a slow reply from overwriting a newer platform's list.

A tag can only go to its own platform

A tag is built for one platform — its family (Nexxen or TTD today) — and can only be pushed there. One push targets a single platform, and the platform drives the selection: the picker always lists every platform, and choosing one auto-selects that platform's tags (disabling the rest). Switch platforms and the selection swaps. A mixed Nexxen + TTD list needs no manual sorting.

Prototype stand-in

In the prototype every tag is a Nexxen or TTD tag, so the platform options are exactly those two. In the final version, tags sync with the platforms directly — the family→platform lock is the prototype stand-in for that sync.

Choosing what to push

  • Until a platform is chosen, nothing is selected — the checklist prompts "Pick a platform to select its tags."
  • Each tag row shows its platform + current status, and — for a tag already pushed — the advertiser + ID it was last assigned to. Tags on other platforms are disabled.
  • A select-all toggle and a live "3 of 6 Nexxen tags selected" count cover the chosen platform; the button reflects the count (Push 3 Tags) and stays disabled until a platform, an advertiser, and ≥1 tag are chosen.

Add + Push / Save + Push

The tag editor has a push button in both modes — Add + Push when creating, Save + Push when editing — so a tag can be pushed the moment it's made or any time later. Either saves the tag, then opens the push flow pre-scoped: platform locked to the tag's family, that one tag pre-selected. With the locked advertiser, it's often a single confirm.

The five states

PushingPush in flight.

Unlink / Link toggle

Each distro row has a link/unlink icon (right of the transcode restart icon) that reflects state and toggles on click: a link-on icon on a Success tag unlinks it → Inactive (target kept); a link-off icon on an Inactive/Error tag relinks the remembered platform → Success; disabled on a Not-pushed/Pushing tag. Both unlink and re-link confirm first — a platform connection shouldn't change by accident (transcode restart is guarded the same way). Prompts are generic, not platform-specific.

In the app

The Push modal

Pick a platform → its tags auto-select. The advertiser is locked once set — the field is disabled, with a lock icon and a "contact support" tooltip. Uncheck any tags to hold back, then push.

The lock is announced before it's set

Because the first push is what sets the lock, the user is told twice: an inline notice appears under the advertiser field the moment an advertiser is chosen, and the first push raises a confirmation — "Lock the advertiser for this platform?" — spelling out that the advertiser locks to every distribution on this platform for the line item, now and for any added later. Other platforms keep their own; a new line item is set up separately. The copy is intentionally generic so it never has to be generated per-platform.

Scoping the real build

Prototype vs. production

In the prototype

  • Advertiser lists are mocked (a fixed set per platform) with simulated latency.
  • Pushing is optimistic — every push lands Success; nothing leaves the browser.
  • Error/rejection is shown only via the ⋯ "Set platform status" affordance.
  • Only the last push target + status is kept per tag.

For production

  • Real per-platform advertiser API (each platform authenticated independently).
  • Real push API returning success / error / rejection — the UI already models the transitions.
  • Surface rejection reasons and a retry path on Error.
  • Persist push history (platform, advertiser, timestamp, outcome).

Still open

Questions for the team

  • Do SSPs use "advertisers," or a different association? Supply-side may bind to a publisher or seat instead — the second dropdown's label would become platform-dependent, and the API would return the field name alongside the list.
  • Should transcode state gate a push? Right now any tag is pushable regardless of transcode status. Should a non-Live tag be blocked or warned first?
  • Re-push semantics. What happens when an already-Successful tag is pushed again — overwrite, version, or no-op?
Try it

Walkthrough

Add distribution tags

Distributions → + Add Distribution Tag, choosing the Nexxen or TTD tab. Each appears with a Not pushed Platform Status.

Add + Push

While adding a Nexxen tag, click Add + Push. The dialog opens with the platform locked to Nexxen and the new tag pre-selected; pick an advertiser and push.

Platform drives the selection

With a mix of tags, open Push Tags to Platform, pick Nexxen → all Nexxen tags auto-select (TTD disabled) → push; then pick The Trade Desk → the selection swaps → push those.

Push just some

After picking a platform, uncheck any of its tags to hold them back before pushing.

Show a rejection

Use a row's ⋯ menu to force Error on the platform status.

Known limits

Not-yet-built

  • No backend or real auth; all data is in the browser and resets if localStorage is cleared.
  • Advertiser lookup and push are simulated (timers + mock data); no request leaves the browser.
  • No push history and no retry / rejection-reason UI yet — both flagged as production work above.
